## 交付物落在哪(目录和文件名已定,不要自己发明)

v1 的模式是内核态逻辑独立成 `.c`,Python 侧用 `BPF(src_file="./bpf/xxx.c")` 加载,展示层只管取数和打印。新模块照搬这个模式:

```
源码/src/
├── bpf/
│   ├── fraginfo.c          # v1,已有,不要动
│   ├── extfraginfo.c       # v1,已有,不要动
│   ├── compactinfo.c       # ★ P0 新增:compaction: 三个 tracepoint
│   └── reclaiminfo.c       # ★ P1 新增:vmscan: 两个 tracepoint
├── extfrag.py              # v1,已有:加分支来选择加载哪个 .c,不新开 py 文件
└── tools/fragstress/       # ★ P-1 新增:纯用户态压力注入器
    ├── *.c                 # 起海量线程 / mmap 后随机 free,普通用户态 C,和 eBPF 无关
    ├── *.sh                # 造小文件、开 socket、调 THP 开关
    └── Makefile
```

三条硬性要求:

1. **P0 和 P1 分两个 `.c`,不许合并。** 理由和 v1 拆 `fraginfo.c` / `extfraginfo.c` 一样:BCC 是加载时现场编译的,合并意味着只想看 reclaim 时也得把 compaction 埋点一起挂上,白付开销;而且分开调试报错定位清楚得多。
2. **`tools/fragstress/` 下的 C 是普通用户态程序,别放进 `src/bpf/`。** 那个目录下只放 BCC 加载的内核态源码,混进去会让人以为压力注入器也是 eBPF。
3. **不新开 Python 文件。** 在 `extfrag.py` 里加参数分支即可。展示层这次不做深:内核态数据能正确打印出来就够了,不要花时间做 TUI、曲线、颜色。

## 已知的坑(初稿踩过,别再踩)

计划书第〇章和 §3.4 有完整说明,这里列出来方便你自查:

1. map key 用 **tid**(`bpf_get_current_pid_tgid()` 完整 u64),不是 `>> 32` 的 tgid —— compaction 是线程行为
2. `mm_compaction_try_to_compact_pages` 是**必需**的外层埋点,不是可选 —— `order` 只有它有,而 begin/end 是 per-zone 的
3. **必须做三重来源过滤**(direct / kcompactd / 手动 `compact_memory`),它们共用同一组埋点,不过滤统计全脏,而且过滤要在内核态做
4. `BPF_LRU_HASH` 是拿"内存泄漏风险"换"静默丢事件",丢掉的恰好是长尾 —— 必须加 `unpaired` 计数器并在输出里报未配对率
5. 扫描页数别用 `free_pfn - migrate_pfn` 硬算 —— 扫描器会重启,会算出负数
6. 慢路径顺序:retry 循环里是**先 direct reclaim 后 direct compaction**;只有 costly order(order > 3)在进循环前有一次提前规整

## 任务报告格式(每阶段结束输出,写成 `报告_P0.md` / `报告_P1.md` 放项目根目录)

评审员靠这份报告判断你做的对不对,所以**要有可核对的原始数据,不要只有结论**:

3. **压力注入效果**(阶段一必须有) —— 施压前后的 `/proc/vmstat` 关键计数器对照表 + `/proc/pagetypeinfo` 的 Unmovable 行变化,证明 §2.4 验收标准过了
4. **交叉验证表** —— 你的工具统计值 vs `/proc/vmstat` 对应计数器 vs PSI,三列并排,**偏差要给出解释**(比如过滤掉的 kcompactd 部分)。对不上就如实写对不上
5. **未配对率** —— 实测多少,是否在可接受范围
6. **一段内核原理复述** —— 用你自己的话讲清这个阶段挂的埋点背后内核在干什么(阶段一讲双扫描器和迁移失败的原因,阶段二讲 direct reclaim 与 kswapd 的分工)。这段是给我面试用的,不要抄计划书原文

报告里不要写"完美实现""效果良好"这类话。跑不通就写跑不通,数据对不上就写对不上 —— 评审员要的是真实状态。
